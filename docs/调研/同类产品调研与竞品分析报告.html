01 结论摘要

这个市场并不缺功能。真正的空位不是“再做一个人物关系图”或“再做一个地图”，而是让这些资料围绕一部长篇小说持续联动，并让作者掌握账户和数据所在的服务器。

功能层面没有单点空白

大纲、素材、地图、人物关系、物品设定和正文编辑，在商业产品或多款开源项目中都能找到成熟实现。

一体化仍集中在商业产品

Campfire、World Anvil、Novelcrafter 等已覆盖多个模块，但数据依赖厂商云端账户；开源产品通常只强于其中一两项。

自托管不是空白，但很早期

本轮样本中出现 novel-it、novel-app、Odysseum 等自有服务器项目，成熟度普遍低；账户隔离与结构化写作结合者更少。

龙吟的胜负手是数据关系

“共享原件＋作品扩展＋人物对绑定关系＋剧情阶段”比模块数量更有辨识度；编辑器速度与可迁移性决定作者愿不愿意长期使用。

核心判断

龙吟不应定位成“功能更多的写作软件”，而应定位成“作者自己掌控的结构化长篇创作工作台”。对外需要讲的不是六个模块，而是一句话：人物、地点、武器、素材和正文始终互相对应，账户与数据运行在自己的服务器上。

02 调研方法与范围

本次调研采用两类样本：一是通过 GitHub 公共 API 检索的写作、世界观构建、自托管写作项目；二是成熟商业产品的公开功能页。产品功能判断以 README 或官方页面明确描述为准，不根据截图猜测未写明的内部数据模型。

GitHub 检索

围绕 novel writing、worldbuilding、story bible、character relationship、self-hosted writing、writing-app 等关键词检索，并逐项核对仓库元数据、许可证和 README。

商业产品核对

覆盖 Campfire、World Anvil、Novelcrafter、Plottr、Scrivener、bibisco，重点看模块边界、账户方式、数据存储和跨书共享。

对照基线

以当前龙吟需求为固定基线：必须登录、账户数据保存在本地服务器、支持外网访问，六类创作数据和正文围绕作品组织。

口径说明

GitHub star 是关注度指标，不是产品质量、维护质量或商业可行性的证明。表中的活跃时间与 star 均为 2026-10-30 查询结果，后续会变化。

3.2 GitHub 上的三个明显信号

传统写作软件的竞争点是大纲、编辑与文件可读性

novelWriter 和 Manuskript 都选择本地文件与纯文本或结构化文本，核心竞争力是可持续写作和可导出，而不是社交或协作。novelWriter 以“人类可读的文本文件”为存储原则，说明目标用户高度重视数据掌控与长期可迁移性。

较新的开源项目普遍转向 AI，而不是补全世界观模块

本轮以 novel-writing 为 topic 的高星项目中，头部大量是 AI 写作技能、Agent 流程或整本生成工具，例如 oh-story-claudecode、chinese-novelist-skill、OpenFic。它们增长快，但解决的是“生成内容”，不是“持续维护作者自己的设定与正文关系”。龙吟若跟着堆 AI，会进入一个供给拥挤且快速变化的战场。

“自托管”已有探索者，但没有成熟的一体化产品

novel-it 已实现多用户隔离、SQLite/PostgreSQL 和反向代理访问；novel-app 采用 Python 后端、网页前端和本地数据目录；Odysseum 则探索自托管 Markdown 与插件。结论是：技术上并不独特，产品完整度才是机会。这些项目 star 很低，不代表需求不存在，说明还没有产品把部署、账户、写作和世界设定同时做好。

3.3 一个值得警惕的概念验证

Wolfden 用 Markdown＋Git 管理 Author → Universe → Series → Book 层级，并用 book/chapter 标记事实生效范围，形成“故事内视角下的 canon”。它和龙吟的“共享原件＋作品扩展＋剧情阶段”方向高度接近，但 Wolfden 仍是早期 CLI 思路、没有成熟 UI。这个样本说明我们的数据思路有合理性，但也说明仅凭数据模型无法建立产品壁垒。

04 商业产品格局

产品核心定位与龙吟重叠的能力数据与账户龙吟可借与需避开的地方

商业产品给出的答案

“全模块＋账户云端”已被验证有付费市场；“本地文件＋自由插件”也已被验证有忠实用户。尚未被充分解决的是两者之间：像本地产品一样掌握数据，又像商业 SaaS 一样随时登录使用，并提供一体化的长篇小说工作流。

06 分模块判断

6.1 正文编辑器：效率是入场券，不是差异化

Scrivener 已经用 Binder、Corkboard、Scrivenings 和快照定义了长篇写作工程的基础体验；novelWriter 则证明纯文本和多文件结构可以支撑长期创作。Notepad++ 给龙吟的参考应当是低干扰、多文档、快速查找替换、异常恢复和清晰的本地保存状态，而不是照搬代码编辑器的视觉。

判断：编辑器必须做到“打开快、写得多、找得到、恢复得了”。如果正文体验落后于 Scrivener 或 novelWriter，其他模块再丰富也难以留住作者。

6.2 大纲：必须从“章节表单”升级成故事结构

Plottr 以可视化时间线和系列圣经建立优势；Campfire 用时间线、故事弧和多书规划把大纲从单章扩展为整个系列。当前龙吟大纲更接近“卷章树＋单章场景节拍”，适合执行，却缺少整本书的主线、冲突和结局方向。

判断：大纲应采用“故事总纲 → 分卷结构 → 章节卡与场景节拍”三级视图。章节卡继续关联人物、地点和资料，避免大纲与正文成为两套孤立系统。

6.3 人物关系：图谱已有强手，龙吟要赢在关系语义

Campfire 的关系模块明确提供关系流程图和家谱；World Anvil 提供家谱与外交关系；Novelcrafter 在 Codex 中提供 Relations。也就是说，画一张人物关系图本身没有竞争壁垒。

龙吟已有的“起点人物＋终点人物＋关系类型＋共享/作品归属＋剧情阶段”比普通无向关系图更接近写作需要。它回答的是“在这一卷里，这两个人是什么关系”，而不是“这两个人曾经是什么关系”。

产品风险

纯图形式关系管理在人物超过 20 个后迅速失控。必须以“当前人物绑定关系列表”为主视图，关系图作为辅助理解，不反过来让用户在一张越来越乱的网里找信息。

6.4 素材与设定库：共享是正确的，独立菜单正在重复

Novelcrafter 的 Codex 支持系列级共享，说明跨书设定复用有真实价值；Plottr 的系列圣经也支持集中维护人物和地点；Scrivener 的研究资料和 Obsidian 的双链则证明作者会把大量素材与稿件放在同一工作区。

但当前龙吟同时存在“设定库”“素材库”“人物关系”“武器设定”四个入口，单部作品内会形成明显重复。共享原件应当属于账户层，作品页面只展示“被本作品引用后的状态和扩展”。

判断：把设定库移到账户级共享库；人物、地点、物品、素材页面通过“引用共享设定”进入。作品内不再单独放一个泛化设定库入口。

6.5 地图：先别做地图绘制器

Campfire 的地图能力是上传地图、创建图层、在地图上钉选元素；World Anvil 和 LegendKeeper 也是“地图＋钉点＋关联条目”的逻辑。这说明作者更关心地点和故事是否关联，而不是软件能否从零画出山川。

判断：第一版只做底图上传、图层、地点标记、地点关联人物与章节。不要投入完整地形绘制、笔刷和奇迹式地图生成，否则研发成本会吞掉写作主线的资源。

6.6 武器与物品：保留需求，但不要做窄

商业世界构建产品普遍使用通用条目或自定义字段管理物品。bibisco 也把地点、物品作为故事元素管理。单独做一个“武器”顶级导航，只适合武器是核心玩法的作品，不适合通用写作平台。

判断：保留武器模板，但归入“物品/设定条目”体系；武器可以预置持有者、状态、材质、能力和来源，未来防具、法宝、丹药也能复用同一结构。

6.7 账户与数据：这是龙吟最清晰的差异，也是最重的责任

商业产品默认账户数据在厂商云端；开源写作软件大多默认单用户本地文件。自托管的 novel-it、novel-app 等已经开始解决账户隔离和反向代理访问，但项目非常早期。

龙吟把账户设为必须入口，并把数据放在用户自己的本地服务器，提供了第三条路线：账户可跨设备使用，数据不交给厂商，网络范围由作者自己决定。这不是一句部署说明，而是产品价值主张，必须在首页、账户页、导出与备份流程中保持一致。

07 龙吟的机会与差异化

7.1 可被市场验证的优势

自有服务器上的账户数据

比传统本地软件更方便访问，比商业云软件更强调数据掌控。竞品中已有早期探索，但没有成熟的一体化体验。

共享原件＋作品扩展

Novelcrafter 系列共享和 Wolfden 的宇宙/系列/书层级都在证明这一需求。龙吟可用明确的覆盖规则避免复制和污染。

能随剧情变化的关系

Campfire 已有关系与故事弧，但“关系状态按作品和卷章生效”仍适合长篇连载和系列小说。

7.2 不构成差异化的地方

  • 人物关系图：Campfire、World Anvil、51mazi 都有类似能力。
  • 地图钉点：Campfire 与 LegendKeeper 已较成熟。
  • 章节大纲：Plottr、Scrivener、Manuskript 等普遍具备。
  • 人物档案、时间线、素材整理：大量写作软件已覆盖。
  • AI 续写与整本生成：开源市场供给拥挤，且与龙吟的手动创作定位不一致。

7.3 建议的产品定位

定位表述

龙吟写作是面向长篇与系列小说作者的结构化创作工作台：账户数据运行在作者自己的服务器上，人物、地点、物品、素材与正文始终互相引用，关系随作品和剧情阶段变化。

目标用户应优先是长篇连载作者、系列小说作者和重视资料掌控的成熟作者。不要先服务“所有写作者”，也不要先与 AI 自动生成工具争夺同一批用户。

08 风险与取舍

8.1 功能范围过大

六个模块加上大纲、设定库和正文工程，实际上已经是多个商业产品的合集。若每个模块都做浅层 CRUD，会在任何一个专业竞品面前都不占优势。应围绕“章节写作时需要什么”决定模块深度，而不是按功能清单平均投入。

8.2 自有服务器带来运维和安全责任

外网访问意味着登录入口暴露在公网。至少需要账户隔离、强密码与登录限流、会话失效、CSRF 防护、TLS 终止、访问日志、定期备份和恢复演练。服务器是用户自己的，不代表安全问题会自动消失；一旦作品丢失，用户仍会归因于产品。

8.3 共享库的所有权歧义

共享人物在 A 作品中被修改时，不能改变 B 作品已经依赖的事实。当前“共享原件＋作品扩展”的方向正确，但 UI 必须明确显示正在编辑哪一层，并阻止用户误以为修改了共享原件。删除共享人物前也要检查所有作品中的引用关系。

8.4 地图成本失控

地图如果从“上传底图和标点”扩展到“绘制山川、自动生成城市、势力范围动画”，就会变成独立产品。第一版应严格限定为底图、图层、标记和关联，并用真实作品验证使用频率后再扩展。

8.5 数据迁移不及竞品

Kindling 已把从 Scrivener、Plottr、yWriter、Obsidian 导入作为卖点。龙吟若没有完整导出、备份和导入能力，作者不会愿意把长篇作品迁入。账户与服务器模式不能成为数据锁定。

8.6 AI 既不能忽视，也不该成为主线

GitHub 新项目的增长高度集中在 AI 生成。龙吟若完全不提供辅助，未来可能被视作传统工具；若过早投入生成，又会稀释“作者掌控和结构化创作”的定位。合理顺序是先让设定和正文形成可检索的上下文，再考虑可选的资料问答、连续性和措辞检查。

09 落地优先级建议

排序依据不是模块数量，而是竞品已经证明的用户底线和龙吟真正能形成差异的部分。

P0
账户、服务器与写作闭环
账户隔离与登录、作品列表、纯文本或 Markdown 正文、自动保存、历史快照、全文查找、完整备份与导出。没有这条闭环，其他模块没有承载基础。
P0
三级故事大纲
故事总纲、分卷结构、章节卡与场景节拍。章节卡可关联人物、地点和资料，能直接进入正文。
P1
共享设定库与人物关系
共享原件与作品扩展分离；关系以人物对为锚点，记录方向、归属与生效阶段。提供列表主视图和关系图辅助视图。
P1
素材引用与反向查找
素材按账户共享，作品保存笔记和章节引用；任意设定能反查被哪些章节使用。
P2
地图与物品模板
地图先做上传底图、图层、标记和关联；武器改成通用物品模板的一个预置类型，避免孤立模块。
P3
可选的连续性辅助
在已有设定和正文之上提供检索、时间线冲突提示和措辞建议。不要以自动生成整章作为核心卖点。
优先级中的取舍

地图和武器不是第一版的核心壁垒，但会被用户用来判断“是不是完整”。因此它们可以做，但必须受控在模板、标记和关联范围内，不能变成独立编辑器。

10 上线前验证清单

  1. 写作闭环验证：让作者从新建作品开始，完成大纲、三章正文、资料关联和历史恢复，全程不使用外部编辑器。
  2. 共享库验证：用两部共享同一人物的作品检验：修改共享原件、添加作品扩展、删除引用和反查影响范围是否清楚。
  3. 关系规模验证：在一个作品中建立至少 30 个人物和 80 条关系，验证筛选、阶段切换和列表性能；确认关系图不是唯一入口。
  4. 地图规模验证：在单张底图上放置至少 100 个地点标记，验证缩放、图层开关和关联详情的响应速度。
  5. 迁移验证：完成 Markdown/JSON/附件导出，再从导出包重新导入，确保正文、关联和附件不丢失。
  6. 外网安全验证：通过反向代理从公网登录，检查未登录访问、跨账户越权、暴力尝试、会话过期和备份恢复。
  7. 用户价值验证：重点观察作者是否真的使用人物关系、地图和武器，而不是只在大纲和正文之间切换；低使用模块应合并，而不是继续扩张。
